## Summary
Diagnosed both failing tests and provided concrete, implementable fixes. Test 1 fails because `hasLocalReproductiveResources()` allows starter carrion for first-birth scavengers when it should not. Test 2 fails due to RNG stream ordering dependency: the shared `audioStream` means each creature consumes RNG sequentially, so population changes shift sound detection rolls. Test 2 is not directly caused by d6f983c but by the upstream RNG architecture.

## Test 1: "requires recurring carrion before starter scavengers reproduce"

**Proximate Cause (with evidence):**
- **Location:** `src/simulation/engine.ts`, lines 134-185 (`hasLocalReproductiveResources`)
- **Issue:** For scavengers on first birth, the function computes `scavengerRange = 6` to search farther (line 161), then returns `hasNearbyCorpse || recentlyFed` (line 183). The `hasNearbyCorpse` variable (line 172) includes ALL corpses within range, even starter carrion (corpses with `lineageId` ending in `_starter_carrion`). The test creates a corpse with `lineageId = 'scavenger_starter_carrion'`, calls `hasLocalReproductiveResources`, and expects `false`. But the function returns `true` because it finds the starter corpse and doesn't filter it out.
- **Comparison:** The function has a `hasGeneratedCorpse` check (lines 173-176) that correctly filters `!other.lineageId.endsWith('_starter_carrion')`, but this is only computed for the 1-cell range and is **never used in the scavenger check**.

**Concrete Fix (for Test 1):**
File: `src/simulation/engine.ts`, lines 165-183

Replace:
```typescript
const nearbyCorpses = strategy === 'scavenger'
  ? spatialIndex.querySquare(creature.x, creature.y, scavengerRange).filter(
    (other) => other.id !== creature.id
      && Math.max(Math.abs(other.x - creature.x), Math.abs(other.y - creature.y)) <= scavengerRange
      && (other.lifecycleState === 'dead' || other.lifecycleState === 'corpse')
  )
  : [];
const hasNearbyCorpse = hasCorpse || nearbyCorpses.length > 0;
const hasGeneratedCorpse = nearby.some((other) =>
  (other.lifecycleState === 'dead' || other.lifecycleState === 'corpse') &&
  !other.lineageId.endsWith('_starter_carrion')
);
const recentlyFed = creature.energy >= supportedEnergy;
if (strategy === 'herbivore') return cellHasProducers || recentlyFed;
if (strategy === 'carnivore') return hasPrey || recentlyFed;
// Scavengers can use any nearby corpse for reproduction, including starter carrion.
// This allows founders to reproduce from initial carrion and sustain themselves until
// generated corpses from hunting/kills become available. #319 fix.
if (strategy === 'scavenger') return hasNearbyCorpse || recentlyFed;
```

With:
```typescript
const nearbyCorpses = strategy === 'scavenger'
  ? spatialIndex.querySquare(creature.x, creature.y, scavengerRange).filter(
    (other) => other.id !== creature.id
      && Math.max(Math.abs(other.x - creature.x), Math.abs(other.y - creature.y)) <= scavengerRange
      && (other.lifecycleState === 'dead' || other.lifecycleState === 'corpse')
  )
  : [];
// For first-birth scavengers, filter nearbyCorpses to exclude starter carrion
const hasGeneratedCorpseInScavengerRange = isFirstBirth
  ? nearbyCorpses.some((other) => !other.lineageId.endsWith('_starter_carrion'))
  : nearbyCorpses.length > 0;
const hasNearbyCorpse = hasCorpse || (strategy === 'scavenger' && isFirstBirth ? hasGeneratedCorpseInScavengerRange : nearbyCorpses.length > 0);
const hasGeneratedCorpse = nearby.some((other) =>
  (other.lifecycleState === 'dead' || other.lifecycleState === 'corpse') &&
  !other.lineageId.endsWith('_starter_carrion')
);
const recentlyFed = creature.energy >= supportedEnergy;
if (strategy === 'herbivore') return cellHasProducers || recentlyFed;
if (strategy === 'carnivore') return hasPrey || recentlyFed;
// Scavengers on first birth require GENERATED corpses (not starter carrion) to reproduce.
// Subsequent births can use any corpse. This enforces recurring carrion requirement.
if (strategy === 'scavenger') return hasNearbyCorpse || recentlyFed;
```

(Alternatively, simpler: change line 183 to `if (strategy === 'scavenger') return (isFirstBirth ? hasGeneratedCorpse : hasNearbyCorpse) || recentlyFed;` but requires extending `hasGeneratedCorpse` search radius to `scavengerRange`.)

## Test 2: "Sound ecology integration > predator investigation: carnivore detects feeding sound from prey"

**Proximate Cause (with evidence):**
- **Location:** `src/simulation/engine.ts`, lines 579-612; `src/simulation/soundEcology.ts`, lines 208-248
- **Issue:** Sound detection uses a shared RNG stream (`audioStream = rngStreams.getStream(RNG_STREAMS.SOUND)` on line 579). During the creature loop (line 581+), each creature calls `detectActiveSounds(..., audioStream.fn)` sequentially, consuming RNG values. For each sound, `detectsSound()` (soundEcology.ts:208-248) calculates a deterministic probability but uses `rng()` to make a probabilistic decision (line 248): `return rng() < detectionProbability;`.
- **Ordering Dependency:** If any previous operation (e.g., Fix 1's reproduction gate change) causes a different set of creatures to exist at the start of Tick 2, the `aliveCreatures` loop iteration order changes. Each prior creature in the loop consumes RNG values before the carnivore gets its turn, shifting what RNG value the carnivore's sound detection roll receives. A higher RNG value (closer to 1.0) fails the detection if `detectionProbability` is moderate (e.g., 0.5–0.8).
- **Math:** Test 2 places herbivore and carnivore at same location (50, 50) with abundant producer biomass. Herbivore should feed in Tick 1, creating a feeding sound. In Tick 2, carnivore should detect it. The detection probability is: `detectionProbability = Math.max(0, intensity - distance * falloff)` ≈ high value (e.g., 0.8–0.95) at distance 0. But the test is currently failing to detect, suggesting the RNG draw is too high (>0.8).

**Concrete Fix (for Test 2) — Option (a): Per-Entity RNG Streams for Sound Detection**

File: `src/simulation/engine.ts`, lines 579 and 612

Current code (lines 578-612):
```typescript
  // Get audio perception stream for sound detection
  const audioStream = rngStreams.getStream(RNG_STREAMS.SOUND);

  for (const creature of aliveCreatures) {
    // ... dispersal logic ...

    // Detect active sounds for this creature (audio perception)
    const detectedSounds = detectActiveSounds(creature, spatiallyBoundedSounds, state.tick, audioStream.fn);
```

Replace with:
```typescript
  for (const creature of aliveCreatures) {
    // ... dispersal logic ...

    // Get entity-level sound detection stream for stable per-creature randomness
    // (prevents unrelated creature births/deaths from shifting this creature's RNG values)
    const entityAudioStream = rngStreams.getEntityStream(RNG_STREAMS.SOUND, creature.id);

    // Detect active sounds for this creature (audio perception)
    const detectedSounds = detectActiveSounds(creature, spatiallyBoundedSounds, state.tick, entityAudioStream.fn);
```

**Rationale:** By using per-entity RNG streams (keyed by `creature.id`), each creature gets a deterministic, stable sequence of RNG values that is independent of:
- Population changes (birth/death of other creatures)
- Iteration order changes
- Other subsystems' RNG consumption

This matches the existing pattern for movement (`rngStreams.getEntityStream(RNG_STREAMS.MOVEMENT, creature.id)` on line 602) and mutation (`rngStreams.getEntityStream(RNG_STREAMS.MUTATION, creature.id)` on line 1059).

**Why this is the right fix:**
- Sound ecology is a per-creature perception phenomenon; each creature should have its own stable sensory RNG, not share one global stream.
- The per-entity pattern is already established in the codebase and is the intended design (see rng.ts lines 174–210 `getEntityStream` method).
- Removes the fragile ordering dependency without changing detection probability math.

## Root Cause Relationship

**Do the two tests share a root cause?**
No. Test 1 fails in `hasLocalReproductiveResources` logic (specific to scavenger carrion filtering). Test 2 fails in RNG stream ordering (shared across all perception). They are independent bugs.

**Does either relate to d6f983c?**
- **Test 1:** Indirectly. The d6f983c change (scavenger-specific `firstBirthUrgency` gate) may have exposed this bug by changing when scavengers can attempt to reproduce, but the root cause is in `hasLocalReproductiveResources` predating d6f983c.
- **Test 2:** No direct link to d6f983c. The d6f983c change is purely about reproduction gates (engine.ts:991–992), which is later in the tick than sound detection (engine.ts:579–612). Test 2's failure is architectural: shared RNG streams in a system with variable population.
