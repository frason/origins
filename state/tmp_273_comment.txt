Confirmed root cause, and it's more widespread than just #160/#161:

**Evidence**
- `git status --short` right now: **93 uncommitted/untracked paths** — spanning #163 (Living
  World core), #160 (overlays/legends), #161 (semantic zoom), #165 (adaptation evidence,
  currently in agent-review), #270/#271 (sound ecology), plus assorted leftovers from older
  closed issues.
- `state/verdict.txt` (karen's latest run, this time against #163) shows the identical pattern
  as #160/#161: 9th round, functional criteria pass (14/14, 24/24, 13/13, 2/2 across 4 test
  suites), sole FAIL is "nothing committed."
- `schedule.json`: `"worker_model": "haiku"`, `"max_turns": 25`. These issues each require
  touching 6-12 files (new components, new modules, several test files, CSS, docs) plus running
  `tsc`/`npm test`/`npm run build` to verify before committing. That easily consumes 25 turns on
  a Haiku worker before it ever reaches the final `git add && git commit` step — which matches
  the failure signature exactly: real, working, tested code sitting in the tree, zero commits,
  every single time, regardless of how explicit the issue brief's commit instructions are.

**Conclusion:** not a git identity/permissions/sandbox bug. It's task sizing vs. worker turn
budget — large multi-file issues dispatched to a 25-turn Haiku worker reliably run out of turns
before the commit step, no matter what the brief says.
